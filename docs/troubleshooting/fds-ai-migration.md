# 🛠️ 이상거래 탐지에 머신러닝을 붙이며 합성 데이터 누수 4건을 잡은 기록

> **한 줄 요약**
>
> 룰베이스 FDS를 ML로 확장하면서 첫 모델이 PR-AUC 1.000을 냈다.
> 성공이 아니라 **모델이 사기 수법이 아니라 학습 데이터를 만든 사람의 습관을 외운 것**이었다.
> 네 번 반복해서 잡아낸 뒤, 다섯 번째는 사람이 아니라 스크립트가 잡도록 만들었다.

## 1. 문제 상황

### 📌 상황

- **프로젝트:** teacat — 티켓팅 + NFT 포토카드 거래 서비스
- **담당 영역:** 백엔드(Spring Boot 4 / Java 21) · NFT 거래 이상거래 심사(FDS)
- **발생 일자:** 2026-09-23 ~ 09-24
- **관련 기술:** PostgreSQL 18, Flyway, scikit-learn, Testcontainers
- **관련 기능:** `NftTradeSettlementWriter.screen`, `TradeRiskModelScorer`, `fds/train.py`

규칙 기반 탐지(R1~R8)는 이미 운영에서 FLAG 모드로 돌고 있었다. 여기에 ML을 얹으려는데
**학습 데이터가 없었다** — 운영 실거래 73건, 관리자 판정 3건, 그중 부정 1건.

부정 사례 1건으로는 어떤 모델도 학습시킬 수 없어서, 사기 대본을 주는 **시뮬레이터**를 먼저 만들었다.
정상 거래 사이에 자전 입찰·순환 거래·매집·계정 탈취를 섞어 넣고, 어느 거래가 어느 대본인지를
`simulation_labels`에 따로 기록하는 방식이다.

### 🚨 증상

```
표본 1569건 (부정 669 / 정상 900), 피처 32개
PR-AUC  1.000
ROC-AUC 1.000
임계 0.5: TP 223  FN 0  FP 0  TN 300
정밀도 1.000  재현율 1.000
```

사기 223건을 하나도 안 놓치고, 정상 300건을 하나도 안 걸었다.

같은 데이터에서 규칙 R1~R8의 재현율은 0.409였다. 규칙이 절반 넘게 놓치는 문제를
모델이 **한 건도 안 틀리고** 풀었다는 뜻인데, 말이 되는 상황이 아니었다.

## 2. 기대 동작

```
모델은 규칙이 못 잡는 패턴(3단 순환·매집 초기)에서 이득을 보되,
규칙이 이미 잘 잡는 것(자전 입찰·계정 탈취)에서는 비슷해야 한다.

오탐도 늘어야 정상이다 — 규칙은 "확실한 것만" 걸어서 오탐 0건이었고,
모델은 확률을 매기므로 애매한 정상 거래를 얼마간 걸 수밖에 없다.

즉 기대치는 PR-AUC 0.85~0.95에 오탐 수 건.
PR-AUC 1.000은 "잘 풀었다"가 아니라 "문제가 샜다"는 신호다.
```

## 3. 원인 추적

### 🔎 가설 1. 모델이 정말 잘한 것이다 (대본이 쉬워서)

**왜 의심했는가**

대본을 내가 짰으니 사기 패턴이 현실보다 뚜렷할 수 있다. 합성 데이터의 한계로 설명되면
받아들이고 넘어갈 수 있는 문제였다.

**확인 방법**

성능 지표가 아니라 **계수**를 봤다. 어떤 피처에 기대어 맞히는지가 진짜 정보다.

```
buyerAccountAgeMinutes           -2.827
minutesSinceFirstDeposit         -2.827   ← 계수가 완전히 같다
buyerDeviceSeenBefore            +0.995
buyerPriorDeviceLogins           +0.995   ← 이것도 같다
```

**확인 결과**

```
기각. 상위 피처가 사기 수법과 아무 상관이 없다.
"계정이 어리면 사기" · "로그인 기록이 있으면 사기" 를 배우고 있었다.
게다가 계수가 소수점 세 자리까지 똑같은 쌍이 둘이나 있다 —
서로 다른 이름의 피처가 사실상 같은 값이라는 뜻이다.
```

### 🔎 가설 2. 규칙 결과(`flagged`·`signals`)가 피처로 섞였다

**왜 의심했는가**

가장 흔한 라벨 누수 경로다. 규칙 판정이 입력에 들어가면 모델은 규칙을 베끼고 끝난다.

**확인 결과**

```
기각. 학습 시작부터 제외하고 있었다(EXCLUDED).
게다가 규칙 재현율이 0.409뿐이라, 규칙을 베꼈다면 1.000이 나올 수도 없다.
```

### 🔎 가설 3. 시뮬레이터가 대본마다 다른 값을 심고 있다 ← **진짜 원인**

**왜 의심했는가**

계수 1·2위가 계정 나이와 첫 충전 시각이다. 둘 다 **내가 배우를 만들 때 정하는 값**이다.

**확인 방법**

```sql
SELECT l.scenario,
       round(avg((f.features->>'buyerAccountAgeMinutes')::numeric)/1440, 1) AS 계정나이_일,
       round(avg((f.features->>'buyerPriorDeviceLogins')::numeric), 2)      AS 타단말로그인
  FROM simulation_labels l
  JOIN nft_trade_risk_features f ON f.trade_id = l.trade_id
 GROUP BY 1 ORDER BY 2;
```

**확인 결과**

```
     scenario     | count | 계정나이_일 | 타단말로그인
------------------+-------+-------------+--------------
 HOARDING         |   324 |        32.0 |         0.00
 CIRCULAR_RING    |   132 |        44.0 |         0.00
 NORMAL           |   900 |       117.2 |         0.00
 ACCOUNT_TAKEOVER |    57 |       120.0 |        12.00
```

확정. 사기 배우는 32~45일, 정상은 117일. **경계가 한 줄로 그어진다.**

원인은 시뮬레이터 코드였다.

```java
traders.add(newActor(now.minusDays(60 + random.nextInt(120))));  // 정상: 60~180일
Actor hoarder = newActor(now.minusDays(35));                     // 매집: 항상 35일
Actor a       = newActor(now.minusDays(50));                     // 순환: 46~50일
```

대본을 쓰면서 "매집범은 최근에 만든 계정이겠지" 하고 자연스럽게 박아 넣은 숫자가
그대로 **라벨을 가리키는 표지**가 됐다.

## 4. 해결 방법

### 💡 해결 전략

```
누수는 "모델을 고쳐서" 해결되지 않는다. 입력에 답이 적혀 있으면
어떤 알고리즘을 쓰든 그 답을 읽는다. 그래서 모델이 아니라 데이터를 고쳤다.

그런데 고칠 때마다 같은 종류가 또 나왔다. 결국 네 번 반복했고,
그 시점에 문제를 다시 정의했다 — "이번 누수를 고치는 것" 이 아니라
"다음 누수를 사람이 아니라 스크립트가 잡게 하는 것" 이 과제다.
```

### 🔧 변경 내용 — 누수 4건

| | 무엇이 샜나 | 원인 | 고친 방법 |
| --- | --- | --- | --- |
| 1차 | `buyerAccountAgeMinutes`<br>`minutesSinceFirstDeposit` | 사기 배우 가입일을 대본마다 박음. 충전은 항상 가입+5분 | 대본과 무관하게 같은 분포(30~180일)에서 추출. 충전은 가입 후 10분~5일 분산 |
| 2차 | `buyerPriorDeviceLogins` | 로그인 이력을 계정 탈취 피해자에게만 심음 | **모든** 배우가 주 단말 4~17회 + 부단말 1~2개 |
| 3차 | `hasSpendHistory` | 사기 배우만 갓 만든 계정이라 거래 이력 없음 | `seedTradeHistory()` 로 모두에게 평범한 매입 이력 |
| 4차 | `baselineVolume`<br>`designTradesInWindow`<br>`recentVolume` | 대본을 종류별로 몰아 돌려 **거래량 = 생성 순서** | 전체 케이스를 섞어서 실행 |

**Before** (4차 누수)

```java
for (int i = 0; i < normalTrades; i++)  normalSale();      // 300건 먼저
for (int i = 0; i < shillCases; i++)    shillCase();       // 그다음 자전 입찰
for (int i = 0; i < circularCases; i++) circularCase();    // 그다음 순환…
```

**After**

```java
List<Runnable> cases = new ArrayList<>();
for (int i = 0; i < normalTrades; i++)  cases.add(this::normalSale);
for (int i = 0; i < shillCases; i++)    cases.add(this::shillCase);
// …
Collections.shuffle(cases, random);
for (Runnable one : cases) tx.executeWithoutResult(s -> one.run());
```

### 🔧 진짜 변경 — 다섯 번째를 기계가 잡게

```python
def warn_single_separators(z, y, scenarios, names, threshold=0.98):
    """피처 하나만으로 어떤 대본이 정상과 거의 갈리는지 본다."""
    normal = scenarios == "NORMAL"
    for scenario in sorted(set(scenarios[y == 1])):
        mask = normal | (scenarios == scenario)
        target = (scenarios[mask] == scenario).astype(int)
        for i, name in enumerate(names):
            auc = roc_auc_score(target, z[mask, i])
            if max(auc, 1 - auc) >= threshold:
                findings.append((scenario, name, auc))
```

🔴 **대본별로 재야 한다.** 처음에는 전체 부정 대 정상으로 쟀더니 **아무것도 잡지 못했다** —
3차 누수가 꾸밈 세탁 한 대본에서만 완벽하게 갈렸고(60/1630건), 전체로는 평범해 보였기 때문이다.
대본별로 고치자마자 **4차 누수까지 같이 나왔다.**

### 변경 포인트

```
1. 라벨과 무관해야 하는 값은 대본이 정하지 못하게 한다
   → newActor() 가 가입 시각을 스스로 뽑는다. 대본이 빠뜨릴 수 없다.

2. 정상에도 있어야 할 신호는 정상에도 심는다
   → 로그인·거래 이력을 모든 배우에게. 현실에서는 누구나 로그인하고 거래한다.

3. 생성 순서가 신호가 되지 않게 섞는다
   → 사기는 정상 거래 사이에 끼어서 일어나지, 몰아서 일어나지 않는다.

4. 검증을 사람의 주의력이 아니라 스크립트에 맡긴다
   → 학습 전에 두 검사가 돈다: 같은 피처 쌍 · 대본별 단독 AUC
```

패턴에서 난다.

### 규칙이 원리적으로 못 잡는 것 두 가지

**3단 순환(A→B→C→A)** — R3의 순환 판정이 "이 두 사람 사이"로 한정돼 있어, 마지막 구간에서
C와 A는 처음 거래하는 사이다. 임계값을 조여도 안 잡힌다.

그런데 처음에는 **모델도 못 잡았다.** 피처를 열어 보니 34개 어디에도 "이 카드가 한 바퀴 돌았다"는
정보가 없었다. **모델을 바꿔서 될 일이 아니라 입력에 정보가 없었던 것이다.** 재귀 CTE로
거래 그래프상 최단 경로를 구하고, "구매자가 이 카드를 전에 가진 적 있나"를 고리 길이와
무관하게 판정하는 피처를 넣고서야 잡혔다.

| 피처 | 3단 순환 닫히는 구간 | 정상 |
| --- | --- | --- |
| `buyerPreviouslyOwnedCard` | 5 / 5 (100%) | 0 / 60 (0%) |

**꾸밈 세탁** — 포카 꾸미기가 붙으면서 "잘 꾸며서 비싸다"가 가격 조작의 알리바이가 됐다.
스티커는 하루 5장까지 공짜라 비용 부담도 없다. R4는 꾸민 카드를 판단하지 않게 하고(오탐 방지),
대신 **행동**을 본다 — 꾸민 지 몇 분 만에 파는가, 꾸민 사람이 파는 사람인가.

## 7. 배운 점

```
1. 성능이 너무 좋으면 먼저 데이터를 의심한다.
   PR-AUC 1.000은 "풀었다"가 아니라 "샜다"는 신호다.

2. 계수를 본다. 점수만 보면 무엇을 배웠는지 알 수 없다.
   선형 모델을 기준선으로 고른 이유가 이것이다 — 설명이 되는 모델은
   "왜 맞히는지"를 물을 수 있고, 그 질문이 네 번 다 버그를 잡아냈다.

3. 합성 데이터는 만든 사람의 습관을 담는다.
   대본을 쓰며 무심코 정한 상수("매집범은 35일 된 계정")가 전부 라벨 표지가 된다.
   라벨과 무관해야 하는 값은 대본이 정하지 못하게 구조로 막아야 한다.

4. 같은 실수를 네 번 하면, 문제를 다시 정의해야 한다.
   "이번 누수를 고친다"가 아니라 "다음 누수를 기계가 잡는다"로.
   네 번 중 네 번을 사람이 찾았다는 것은 다섯 번째를 놓친다는 뜻이다.

5. 검사를 만들 때도 측정 단위를 틀리면 아무것도 못 잡는다.
   전체 부정 대 정상으로 쟀을 때는 0건이었고, 대본별로 바꾸자 2건이 나왔다.
   "검사가 통과했다"가 "문제가 없다"는 뜻은 아니다.

6. 모델 성능이 좋아도 분포가 다르면 실전에서 무너진다.
   합성 시장은 200원대인데 dev 실거래에는 98,900원이 있었고,
   그 한 피처가 z에 +1710을 밀어 넣어 모든 거래가 1.000이 됐다.
   자르기(winsorize)를 학습·서빙 양쪽에 걸어 z를 +1744 → 최대 +61.6으로 묶었다.

7. 안전장치가 정상 동작을 막지 않는지도 재야 한다.
   로짓 상한을 15로 걸었더니 가장 확실한 탐지 5건이 "판단 불가"로 빠졌다.
   부정 거래의 z 분포(-3.2 ~ +15.7)를 재 보고서야 알았다.
```

## 8. 다음에 같은 문제가 발생한다면

```
[1] 지표보다 계수·중요도를 먼저 본다
    상위 피처가 도메인 상식과 맞는지. 계수가 같은 쌍이 있는지.

[2] 학습 전에 자동 검사를 통과시킨다
    python fds/train.py 가 먼저 경고한다.
      - 상관 |r| >= 0.999 인 피처 쌍
      - 대본별 단독 AUC >= 0.98 인 피처
      - 상수 열(대본 전부에서 같은 값)

[3] 대본별 피처 분포를 직접 본다
    SELECT l.scenario, avg((f.features->>'의심되는피처')::numeric)
      FROM simulation_labels l
      JOIN nft_trade_risk_features f ON f.trade_id = l.trade_id
     GROUP BY 1 ORDER BY 2;

[4] 검증은 반드시 배치 단위로 자른다
    씨앗을 달리한 판을 최소 3개 만들고 마지막 판을 통째로 남긴다.

[5] 모델을 바꿀 때마다 skew 를 잰다
    python fds/verify_skew.py --model server/src/main/resources/fds/model.json

[6] 실제 데이터의 분포를 먼저 본다
    합성 데이터를 만들기 전에 운영 DB의 가격·빈도 분포를 확인한다.
    이번에 이 단계를 건너뛰어서 dev 실거래가 전부 1.000이 나왔다.
```
