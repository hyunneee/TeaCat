# 티캣(teacat) 포팅 매뉴얼

이 문서는 **Ubuntu EC2 한 대에 개발·운영 환경을 새로 설치하는 사람**을 위한 안내서입니다. 위에서 아래로 따라 하면 됩니다. 명령어는 별도 표시가 없으면 **EC2에 SSH로 접속한 뒤 Bash에서 실행**합니다. 관리자 PC에서 접속할 때는 `ssh -i <개인키_경로> ubuntu@<서버_공인_IP>`를 사용합니다. 꺾쇠 안의 값은 실제 경로와 IP로 바꾸고 꺾쇠 자체는 입력하지 않습니다. `~/teacat-src`는 저장소 사본, `~/teacat`은 컨테이너가 읽는 배포 파일의 위치입니다. Jenkins도 후자의 절대 경로인 `/home/ubuntu/teacat`을 사용하므로 서버 계정은 `ubuntu`를 기준으로 설명합니다.

먼저 GitLab 저장소 읽기 권한, EC2 SSH 권한, 두 도메인의 DNS 수정 권한을 준비하세요. 서버에서 인증서 발급·이미지 다운로드·Gradle/npm 의존성 설치·프론트 모델 다운로드를 할 수 있도록 외부 네트워크도 필요합니다. 운영 기능까지 확인하려면 기존에 배포한 컨트랙트의 역할이 있는 키와 니모닉, 토스·Pinata 등 외부 서비스 계정도 필요합니다. **실제 시크릿은 이 문서나 저장소에 넣지 마세요.** 값을 전달받지 못했다면 임의의 운영 키를 만들어 대체하지 말고 담당자에게 요청하세요.

처음 설치할 때의 순서는 **DNS·방화벽 확인 → 저장소와 배포 폴더 준비 → HTTPS 인증서 발급 → 시크릿 파일 작성 → Jenkins 또는 수동 배포 → 동작 확인**입니다. 이미 운영 중인 서버라면 초기화 명령을 반복하지 말고 6장의 배포 절차부터 확인하세요.

이 문서에서 **compose 파일**은 여러 컨테이너의 실행 설정을 모아 둔 YAML 파일, **`.env` 파일**은 비밀번호와 외부 서비스 키를 담는 파일입니다. **Flyway**는 서버가 시작할 때 DB 테이블을 만드는 마이그레이션 도구입니다. **블루-그린 배포**는 운영 서버를 두 벌(`blue`와 `green`) 준비해 새 서버가 정상 기동한 뒤 nginx가 받는 대상을 바꾸는 방식입니다.

| 환경 | 주소 | 배포 브랜치 |
|---|---|---|
| 운영 | https://teacat.site | `master` |
| 개발 | https://dev.teacat.site | `dev` |
| 모니터링 (Grafana) | https://teacat.site/dashboard/ | — |
| Jenkins | `http://서버_공인_IP:9090` | — |

## 3. 시스템 구성

한 대의 EC2 위에 운영·개발 스택이 함께 올라가고, 앞단 nginx 하나가 두 도메인을 모두 받습니다.
모든 컨테이너는 외부 도커 네트워크 `teacat-net` 에 붙습니다.

```
                  ┌───────────── nginx (80/443) ─────────────┐
                  │  teacat.site          dev.teacat.site    │
                  └────┬──────────────────────┬──────────────┘
  /            → frontend/prod (정적)    frontend/dev (정적)
  /api/        → prod-server-blue|green   dev-server         (:8080)
  /storage/    → prod-minio               dev-minio          (:9000)
  /dashboard/  → mon-grafana (:3000)

  prod-server ─┬─ prod-postgres / prod-redis / prod-rabbitmq / prod-minio
               └─ prod-blockchain (:4000, 내부 전용) ── SSAFY 체인 RPC
```

### 3-1. compose 프로젝트

| 파일 | 프로젝트 이름 | 내용 |
|---|---|---|
| `docker-compose.proxy.yml` | (폴더명) | nginx, certbot — 두 환경 공용 |
| `docker-compose.prod.yml` | `teacat-prod` | 운영 앱 스택 (서버 블루-그린) |
| `docker-compose.dev.yml` | `teacat-dev` | 개발 앱 스택 (서버 단일) |
| `docker-compose.monitoring.yml` | `teacat-monitoring` | 모니터링 스택 (dev·prod 함께 감시) |
| `docker-compose.jenkins.yml` | `teacat-jenkins` | Jenkins |
| `docker-compose.yml` | — | **로컬 개발용** 인프라 (postgres·redis·rabbitmq·minio) |

### 3-2. 포트

| 포트 | 대상 | 외부 공개 |
|---|---|---|
| 80, 443 | nginx | 공개 |
| 9090 | Jenkins (컨테이너 8080) | 공개 — **보안그룹에서 팀 IP 로 제한 권장** |
| 3000 | Grafana | 호스트의 `127.0.0.1`에만 바인딩 (일반 접속은 `/dashboard/`) |
| 8080 | Spring API | 비공개 (nginx 가 프록시) |
| 8081 | Spring Actuator (관리 포트) | 비공개 (`teacat-net` 내부에서만) |
| 4000 | blockchain API | 비공개 (니모닉을 쥔 프로세스라 server 만 접근) |
| 5432 / 6379 / 5672 / 9000 | postgres / redis / rabbitmq / minio | 비공개 (DB는 `docker exec`로 접속) |

Spring 의 context-path 는 `/api` 이므로 nginx 는 프리픽스를 떼지 않고 그대로 넘깁니다.

## 4. 서버 초기 세팅 (처음 한 번)

### 4-1. Docker 설치

EC2 보안그룹에서 **SSH 22번(관리자 IP만), HTTP 80번, HTTPS 443번**을 허용하고, 두 도메인의 A 레코드가 이 인스턴스의 공인 IP를 가리키는지 확인합니다. Jenkins를 웹에서 열어야 한다면 9090번도 **팀 IP에만** 허용합니다. 새 Ubuntu 서버라면 아래 명령으로 Docker Engine과 Compose v2 플러그인을 설치합니다. 이미 Docker가 설치된 서버에서는 기존 컨테이너와 패키지 구성을 먼저 확인하고 설치 부분을 건너뛰세요. [Docker 공식 Ubuntu 설치 안내](https://docs.docker.com/engine/install/ubuntu/)를 기준으로 한 명령입니다.

```bash
sudo apt update
sudo apt install -y ca-certificates curl git
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker ubuntu
```

마지막 명령을 실행했다면 **SSH 연결을 끊고 `ubuntu`로 다시 접속**해야 그룹 권한이 적용됩니다. Docker 그룹은 호스트를 관리할 수 있는 높은 권한이므로 다른 사용자에게 무분별하게 부여하지 마세요. 재접속 후 아래 세 명령을 확인합니다.

```bash
docker --version
docker compose version
docker run --rm hello-world
```

세 명령이 모두 성공해야 다음 단계로 갑니다. 권한 오류가 나면 `ubuntu` 계정으로 재접속했는지 확인하세요. 이미지 다운로드가 실패하면 서버의 외부 네트워크를 확인합니다.

### 4-2. 저장소·배포 폴더·네트워크

저장소 사본과 배포 폴더를 분리합니다. GitLab 주소는 팀에서 받은 주소를 입력합니다. 비공개 저장소라면 해당 계정의 접근 권한도 필요합니다.

```bash
read -r -p 'GitLab 저장소 URL: ' REPOSITORY_URL
git clone "$REPOSITORY_URL" "$HOME/teacat-src"
mkdir -p ~/teacat/{nginx/conf.d,frontend/dev,frontend/prod,certbot/conf,certbot/www,jenkins,monitoring/alertmanager}
cd ~/teacat-src
cp docker/docker-compose.proxy.yml docker/docker-compose.jenkins.yml \
  docker/docker-compose.dev.yml docker/docker-compose.prod.yml ~/teacat/
cp docker/nginx/nginx.conf ~/teacat/nginx/
cp -a docker/jenkins/. ~/teacat/jenkins/
docker network inspect teacat-net >/dev/null 2>&1 || docker network create teacat-net
```

`~/teacat`에는 compose 파일이 바로 놓입니다. `~/teacat/docker/`를 만들거나 그 안에서 compose를 실행하지 마세요. `~/teacat-src`는 이후 수동 빌드에 쓰고, Jenkins는 자신의 워크스페이스에서 저장소를 체크아웃합니다.

이후 배포에서 파일을 누가 갱신하는지도 확인해 두세요.

| 저장소 | 서버 (`~/teacat/…`) | 이후 관리 |
|---|---|---|
| `docker/docker-compose.proxy.yml` | `docker-compose.proxy.yml` | **수동** (두 환경 공용이라 자동으로 덮지 않음) |
| `docker/nginx/nginx.conf` | `nginx/nginx.conf` | **수동** |
| `docker/docker-compose.jenkins.yml` | `docker-compose.jenkins.yml` | 수동 |
| `docker/jenkins/` | `jenkins/` | 수동 |
| `docker/nginx/conf.d/{dev,prod}.conf` | `nginx/conf.d/` | 인증서 발급 후 복사, 이후 Jenkins 자동 |
| `docker/nginx/conf.d/prod-backend.inc` | `nginx/conf.d/` | 인증서 발급 후 복사, 이후 **서버 파일이 정답** |
| `docker/docker-compose.{dev,prod}.yml` | 같은 이름 | 처음 복사, 이후 Jenkins 자동 |
| `docker/docker-compose.monitoring.yml`, `docker/monitoring/` | 같은 이름 | Jenkins 자동 |

### 4-3. 도메인과 HTTPS 인증서

**처음 발급할 때만** 아래 임시 HTTP 설정을 사용합니다. 실제 `prod.conf`·`dev.conf`는 아직 복사하지 마세요. 두 파일의 HTTPS 설정은 인증서를 참조하므로 먼저 넣으면 nginx가 기동하지 않습니다.

```bash
cat > ~/teacat/nginx/conf.d/bootstrap.conf <<'EOF'
server {
    listen 80;
    server_name teacat.site dev.teacat.site;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
}
EOF
cd ~/teacat
docker compose -f docker-compose.proxy.yml up -d nginx
```

두 도메인의 DNS가 맞고 외부에서 80번 포트로 접속할 수 있어야 발급됩니다. Let's Encrypt 만료 안내를 받을 이메일을 입력한 뒤 두 도메인을 **한 인증서**에 등록합니다.

```bash
read -r -p '인증서 알림 이메일: ' CERT_EMAIL
docker compose -f docker-compose.proxy.yml run --rm --entrypoint certbot certbot \
  certonly --webroot -w /var/www/certbot \
  -d teacat.site -d dev.teacat.site \
  --email "$CERT_EMAIL" --agree-tos --no-eff-email
```

발급에 성공하면 인증서 파일이 만들어졌는지 확인하고 실제 설정을 넣습니다. `nginx -t`가 성공한 경우에만 설정을 다시 읽게 하세요.

```bash
test -f ~/teacat/certbot/conf/live/teacat.site/fullchain.pem || { echo '인증서 발급 결과를 확인하세요'; exit 1; }
cp ~/teacat-src/docker/nginx/conf.d/dev.conf ~/teacat/nginx/conf.d/
cp ~/teacat-src/docker/nginx/conf.d/prod.conf ~/teacat/nginx/conf.d/
cp ~/teacat-src/docker/nginx/conf.d/prod-backend.inc ~/teacat/nginx/conf.d/
rm ~/teacat/nginx/conf.d/bootstrap.conf
docker exec nginx nginx -t && docker exec nginx nginx -s reload
docker compose -f docker-compose.proxy.yml up -d certbot
```

인증서는 `~/teacat/certbot/conf/live/teacat.site/`에 저장되며, certbot 컨테이너가 12시간마다 갱신을 시도합니다. 이 폴더는 재설치할 때도 보존해야 합니다. **아직 앱을 배포하지 않았다면 정적 파일이 없어 화면이 열리지 않거나 API가 502를 보일 수 있습니다.** 다음 단계에서 서버와 프론트를 올립니다.

### 4-4. 시크릿 파일 준비

저장소의 **예시 파일만** 복사합니다. 기존 파일이 있으면 덮어쓰지 않습니다. 파일별로 5장의 필수 값을 실제 값으로 채운 뒤 접근 권한을 제한하세요. 아래 마지막 파일은 예시 웹후크 URL을 그대로 두면 알림이 가지 않으므로 실제 URL로 교체해야 합니다.

```bash
cd ~/teacat
umask 077
cp -n ~/teacat-src/docker/.env.dev.example .env.dev
cp -n ~/teacat-src/docker/.env.dev.chain.example .env.dev.chain
cp -n ~/teacat-src/docker/.env.prod.example .env.prod
cp -n ~/teacat-src/docker/.env.monitoring.example .env.monitoring
cp -n ~/teacat-src/docker/monitoring/alertmanager/webhook_url.example monitoring/alertmanager/webhook_url
chmod 600 .env.dev .env.dev.chain .env.prod .env.monitoring monitoring/alertmanager/webhook_url
```

편집기로 값을 채운 후에는 `docker compose -f docker-compose.dev.yml --env-file .env.dev config --quiet`와 운영용 `docker compose -f docker-compose.prod.yml --env-file .env.prod config --quiet`를 실행해 필수 값 누락과 compose 문법 오류를 확인합니다. 이 검사는 키의 **실제 권한이나 외부 서비스 접속까지** 확인하지는 않습니다. **`docker compose config`의 전체 출력에는 시크릿이 보일 수 있으므로 로그나 채팅에 붙이지 마세요.**

### 4-5. Jenkins

```bash
cd ~/teacat && docker compose -f docker-compose.jenkins.yml up -d --build
```

- 이미지는 `jenkins/jenkins:lts` 에 docker CLI 와 compose 플러그인만 추가한 것입니다. 호스트의 `/var/run/docker.sock` 을 빌려 씁니다 (DinD 아님).
- `/home/ubuntu/teacat` 을 **호스트와 같은 경로**로 마운트합니다. compose 의 상대 경로를 호스트 도커 데몬이 해석하기 때문입니다.
- 🔴 `DOCKER_BUILDKIT` 을 켜지 마세요. 이미지에 buildx 가 없어서 빌드가 실패합니다.

Jenkins 설정:

1. `http://<서버_공인_IP>:9090`을 열고 초기 관리자 비밀번호를 입력합니다. EC2 셸에서 `cat ~/teacat/jenkins/jenkins_home/secrets/initialAdminPassword`로 확인할 수 있습니다. 비밀번호를 채팅이나 공개 로그에 붙이지 마세요.
2. 플러그인: 권장 플러그인과 GitLab 연동 플러그인을 설치합니다.
3. 저장소 URL과 접근 자격증명을 등록하고 **Multibranch Pipeline** 잡을 만듭니다. Script Path는 저장소 루트의 `Jenkinsfile`입니다. `dev`·`master` 브랜치를 검색하도록 설정합니다. 다른 브랜치는 배포 대상이 아니라 파이프라인에서 중지됩니다.
4. 첫 실행 **전에** 아래 Credentials를 `Secret text` 유형으로 등록합니다. ID의 철자를 Jenkinsfile과 똑같이 입력하세요.

| ID | 값 | 없으면 |
|---|---|---|
| `mm-webhook` | Mattermost 들어오는 웹후크 URL (배포 성공/실패 알림) | 성공·실패 알림 단계가 실패하므로 **첫 배포 전에 등록** |
| `teacat-analytics-key` | `.env.prod` 의 `ANALYTICS_INTERNAL_API_KEY` 와 같은 값 | 배포 마커만 안 남음 (배포는 성공) |

5. **빈 DB로 처음 설치한다면 개발·운영 모두 6-3의 수동 순서로 서버를 먼저 기동**합니다. 그 뒤 `dev` 브랜치를 Jenkins에서 수동으로 한 번 실행하고 콘솔 로그에서 실패 단계가 없는지 확인합니다. 이미 설치된 환경이라면 수동 설치 절차 없이 `dev`부터 실행하면 됩니다.
6. GitLab 웹후크를 이 잡의 트리거 안내에 표시된 URL로 설정합니다. URL은 Jenkins 잡 유형과 플러그인 설정에 따라 달라지므로 임의로 만들지 마세요. `dev`에 시험 커밋을 푸시한 뒤 자동 실행되는지 확인합니다.

## 5. 환경변수

시크릿은 저장소에 없습니다. 4-4에서 복사한 예시 파일의 빈 값을 채우세요. 일반 비밀번호는 값마다 `openssl rand -hex 24`, JWT 키는 `openssl rand -base64 48`로 만들 수 있습니다. **PostgreSQL 비밀번호에는 특히 URL에서 의미가 있는 `/`, `@`, `:` 등을 피하세요.** 블록체인 서비스의 `DATABASE_URL`에 이 비밀번호가 들어갑니다. 이미 운영 중인 DB 비밀번호나 니모닉은 새로 생성하지 말고 기존 값을 안전하게 전달받아 사용합니다.

| 서버 경로 | 예시 파일 | 읽는 곳 |
|---|---|---|
| `~/teacat/.env.prod` | `docker/.env.prod.example` | 운영 compose 전체 (변수 보간) |
| `~/teacat/.env.dev` | `docker/.env.dev.example` | 개발 compose + dev-server (`env_file`) |
| `~/teacat/.env.dev.chain` | `docker/.env.dev.chain.example` | dev-blockchain 만 (`env_file`) |
| `~/teacat/.env.monitoring` | `docker/.env.monitoring.example` | 모니터링 compose |
| `~/teacat/monitoring/alertmanager/webhook_url` | `docker/monitoring/alertmanager/webhook_url.example` | Alertmanager (Mattermost 알림) |
| `~/teacat/.sentry-auth-token` | — | 프론트 빌드 시 소스맵 업로드 (없으면 건너뜀) |

> 🔴 운영과 개발의 **DB·Redis·RabbitMQ 비밀번호, JWT 키, 마스터 니모닉, 내부 API 키는 서로 다르게** 만듭니다. `JWT_SECRET`이 같으면 개발 토큰이 운영에서도 통하고, `MASTER_MNEMONIC`이 같으면 같은 파생 주소를 사용합니다. 단, 두 환경이 같은 컨트랙트를 사용하므로 오퍼레이터·컨트랙트 역할 키는 해당 컨트랙트에 권한이 있는 주소를 확인한 뒤 정해야 합니다. 무작위 키로 교체하면 권한이 필요한 거래가 실패할 수 있습니다.
> 🔴 `POSTGRES_PASSWORD` 는 볼륨을 처음 만들 때 한 번만 적용됩니다. 처음에 확정하세요.

### 5-1. `.env.prod`

compose 파일에서 `:?`로 검사하는 값이 비어 있으면 **compose 설정을 읽는 단계에서 오류가 나고 컨테이너가 기동하지 않습니다**.

| 변수 | 필수 | 설명 |
|---|---|---|

| `POSTGRES_PASSWORD` | ● | DB 비밀번호 |

| `MINIO_BUCKET` | | 기본 `teacat`. 없으면 서버가 만듦 |
| `JWT_SECRET` | ● | 32바이트 이상 |
| `SSAFY_CLIENT_SECRET` | | SSAFY 로그인. 비면 그 기능만 비활성 |

> ⚠️ **개발·운영이 같은 컨트랙트를 공유**합니다. 캣머니 시드 발행 멱등키(`WALLET_SEED:{파생인덱스}`)가 두 환경에서 겹칠 수 있습니다. **새 운영 DB에서 첫 가입을 받기 전에** 운영 시퀀스를 개발에서 사용한 범위와 겹치지 않게 조정하세요. 개발 환경에서 지금까지 사용한 최대 인덱스와 앞으로 사용할 범위를 담당자에게 확인해 **겹치지 않는 운영 시작값**을 정합니다. Flyway가 시퀀스를 만든 **서버 첫 기동 후**, 회원가입을 열기 전에 6-3의 명령으로 적용합니다. 이미 회원이 있는 운영 DB의 시퀀스를 임의로 재설정하면 안 됩니다.

### 5-2. `.env.dev` / `.env.dev.chain`

`.env.dev` 는 `.env.prod` 와 거의 같되, dev-server 가 `env_file` 로 통째로 읽으므로 **Spring 이 읽는 이름 그대로** 적습니다. 결제·IPFS 키가 비어 있어도 서버는 뜨고 해당 기능만 오류를 냅니다. 토스 키는 `test_` 로 시작하는 테스트 키를 씁니다.

니모닉과 개인키(`MASTER_MNEMONIC`, `OPERATOR_PRIVATE_KEY`, `CONTRACT_OPERATOR_PRIVATE_KEY`, `DRAW_SEED_SECRET`)는 server 에 넘어가지 않도록 `.env.dev.chain` 에 따로 둡니다.
`.env.dev`와 `.env.dev.chain`의 `INTERNAL_API_KEY`를 따로 만들지 마세요. 공유 키는 **`.env.dev`에 한 번만** 두고 compose가 두 컨테이너에 전달합니다. `.env.dev.chain`의 역할 키는 팀이 배포한 컨트랙트에 맞는 값인지 확인해야 합니다.

### 5-4. 프론트엔드 빌드 값

프론트 값(`VITE_*`)은 **빌드할 때 번들에 박힙니다.** 공개 값만 넣습니다.
배포 빌드에서는 `client/.env.production` + Jenkins 가 넘기는 `--build-arg` 를 씁니다.

| 값 | 넘기는 곳 |
|---|---|
| `VITE_USE_MOCK` | Jenkinsfile (현재 `true`; 실제 API 연결이 필요한 화면은 배포 전에 이 설정의 영향을 확인) |
| `VITE_SENTRY_ENVIRONMENT`, `VITE_SENTRY_RELEASE` | Jenkinsfile (`dev`/`prod`, `teacat-client@<커밋>`) |
| `VITE_CLARITY_PROJECT_ID`, `VITE_GA_MEASUREMENT_ID` | Jenkinsfile (운영만 켬) |
| `VITE_TOSS_CLIENT_KEY`, `VITE_SENTRY_DSN` 등 | `client/.env.production` |
| `SENTRY_AUTH_TOKEN` | `~/teacat/.sentry-auth-token` (VITE_ 가 아님 — 번들에 들어가면 안 됨) |

현재 저장소의 `client/.env.production`에는 **토스 문서용 테스트 클라이언트 키**가 들어 있습니다. 운영 `.env.prod`에 `live_` 시크릿 키를 넣고 결제를 실제로 받으려면, 프론트도 **같은 운영 상점의 live 클라이언트 키**로 바꿔 다시 빌드해야 합니다. 두 키의 환경이 다르면 결제가 정상 승인되지 않습니다. 클라이언트 키는 공개 값이지만 `TOSS_SECRET_KEY`는 프론트 파일에 넣으면 안 됩니다. 현재 Jenkins의 `VITE_USE_MOCK=true`도 일부 화면에 목업 응답을 사용하므로 운영 전 실제 API 연결 범위를 확인하세요.

## 6. 빌드 및 배포

### 6-1. 자동 배포 (Jenkins)

4-5에서 Jenkins 잡과 웹후크를 설정한 뒤에는 `dev`에 push하면 개발 서버, `master`에 push하면 운영 서버로 배포됩니다. **빈 DB로 처음 설치할 때는 개발·운영 모두 6-3의 수동 순서로 서버를 먼저 띄워 Flyway 스키마를 만드세요.** 운영은 파생 인덱스 구간도 조정한 뒤 회원가입을 열어야 합니다. 수동 설치 후에는 Jenkins에서 `dev`를 먼저 실행해 시크릿·도메인·컨테이너 상태를 확인하고, 그다음 `master`를 실행합니다. 파이프라인 단계:

1. **환경 결정** — 브랜치로 `dev`/`prod` 결정, 태그는 짧은 커밋 해시
2. **사전 점검** — `.env.<env>`·nginx 폴더·`frontend/<env>`·`teacat-net` 존재 확인, **Flyway 마이그레이션 버전 중복 검사**
3. **변경 감지** — 직전 성공 커밋과 비교해 바뀐 서비스만 빌드 (불확실하면 전부 빌드)
4. **빌드** — `teacat-client:<env>-<tag>`, `teacat-server:<env>`, `teacat-blockchain:<env>` 이미지 빌드
5. **프론트 배포** — 빌드 이미지에서 `/dist` 를 꺼내 `~/teacat/frontend/<env>/` 에 덮어쓰기
6. **설정 동기화** — 해당 환경의 nginx conf 와 compose 파일 복사
7. **앱 배포** — 개발은 `docker compose up -d`, 운영은 블루-그린 (6-2)
8. **nginx 적용** — `nginx -t` 후 reload
9. **기동 확인** — 서버 로그 `Started TeacatApplication` 및 도메인 응답 확인 (운영 트래픽 전환 전에는 Actuator `UP`도 확인)
10. **모니터링 배포** — 설정 동기화, `promtool` 검사, 스택 up, 해당 환경 타겟 UP 확인 (실패 시 빌드 UNSTABLE)
11. **알림** — Mattermost 로 성공/실패 전송, 운영은 배포 마커 기록

### 6-2. 운영 블루-그린 배포

운영 서버 컨테이너는 `prod-server-blue` / `prod-server-green` 두 벌입니다. 평소에는 하나만 뜨고, 전환 중에만 잠시 둘 다 뜹니다.
nginx 가 어느 쪽을 보는지는 `~/teacat/nginx/conf.d/prod-backend.inc` 의 한 줄이 정합니다.

```
set $api http://prod-server-blue:8080;
```

순서:

1. 인프라(postgres·redis·rabbitmq·minio)를 `--wait` 로 올림
2. 유휴 색을 새 이미지로 `--no-deps --force-recreate` 기동
3. `http://prod-server-<새색>:8081/actuator/health` 가 `UP` 이 될 때까지 대기 (최대 5분)
4. blockchain 재기동 (server 의 Flyway 가 끝난 뒤여야 스키마 검사를 통과)
5. `prod-backend.inc` 를 새 색으로 바꾸고 `nginx -t` → reload
6. 옛 색은 **stop 만** (지우지 않음)

3·4단계에서 실패하면 nginx 를 건드리지 않으므로 옛 색이 계속 트래픽을 받습니다.

**전환 후 이전 서버로 되돌릴 때**는 컨테이너와 nginx 대상 **둘 다** 바꿉니다. 먼저 현재 대상과 두 컨테이너의 상태를 확인하고, 실제로 되돌릴 색을 고르세요.

```bash
cat ~/teacat/nginx/conf.d/prod-backend.inc
docker ps -a --filter 'name=prod-server-' --format '{{.Names}} {{.Status}}'
ROLLBACK_COLOR=blue  # 예시: 직전 서버가 blue일 때만 blue로 둡니다
docker start "prod-server-$ROLLBACK_COLOR"
cp ~/teacat/nginx/conf.d/prod-backend.inc ~/teacat/nginx/conf.d/prod-backend.inc.bak
printf 'set $api http://prod-server-%s:8080;\n' "$ROLLBACK_COLOR" \
  > ~/teacat/nginx/conf.d/prod-backend.inc
docker exec nginx nginx -t && docker exec nginx nginx -s reload
```

`nginx -t`가 실패하면 `.bak` 내용을 원래 파일에 복사하고 원인을 고친 뒤 다시 검사하세요. 이 절차는 **애플리케이션 트래픽만** 되돌립니다. Flyway가 바꾼 DB 스키마를 자동으로 되돌리지 않으므로, 마이그레이션은 옛 버전과 호환되게 작성해야 합니다.

### 6-3. 수동 배포

Jenkins를 쓰지 못하거나 첫 설치를 손으로 검증할 때 사용합니다. **4장의 서버 준비와 5장의 시크릿 입력을 먼저 끝내야 합니다.** 아래 예시는 운영 첫 배포입니다. 기존 운영 서버의 색을 바꿀 때는 이 절차를 그대로 반복하지 말고 6-2의 블루-그린 순서를 따르세요.

1. 저장소의 `master`를 최신으로 맞추고 이미지를 만듭니다. 빌드는 `~/teacat-src`에서, compose는 `~/teacat`에서 실행합니다. 프론트의 `VITE_*` 값은 이때 번들에 들어갑니다.

   ```bash
   cd ~/teacat-src
   git switch master
   git pull --ff-only
   docker build -t teacat-server:prod ./server
   docker build -t teacat-blockchain:prod ./blockchain
   docker build -t teacat-client:prod-manual \
     --build-arg VITE_USE_MOCK=true \
     --build-arg VITE_SENTRY_ENVIRONMENT=prod ./client
   cp docker/docker-compose.prod.yml ~/teacat/
   ```

   `client/.env.production`은 저장소의 공개 빌드 값입니다. 실제 결제 클라이언트 키·분석 ID·Sentry DSN을 적용할 계획이라면 빌드 전에 5-4의 값을 확인하세요. 시크릿 키는 넣지 마세요.

2. 인프라만 올리고 상태를 기다립니다. **서비스 이름 없이 `up -d`를 실행하면 운영 blue·green 두 서버가 함께 뜹니다.**

   ```bash
   cd ~/teacat
   docker compose -f docker-compose.prod.yml --env-file .env.prod \
     up -d --wait postgres redis rabbitmq minio
   docker compose -f docker-compose.prod.yml --env-file .env.prod ps
   ```

3. 첫 서버는 `blue`로 시작합니다. `--no-deps`가 중요합니다. 빼면 compose가 의존성을 따라 블록체인을 서버보다 먼저 띄울 수 있습니다.

   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.prod \
     up -d --no-deps server-blue
   docker logs --tail 80 prod-server-blue
   docker exec prod-server-blue wget -qO- http://127.0.0.1:8081/actuator/health
   ```

   마지막 명령에 `"status":"UP"`가 나올 때까지 기다립니다. 처음에는 Flyway 마이그레이션 때문에 수십 초 걸릴 수 있습니다. 컨테이너가 종료되거나 5분이 지나도 `UP`이 아니면 `docker logs --tail 100 prod-server-blue`로 원인을 확인하고 **다음 단계로 넘어가지 마세요.**

4. **새 운영 DB일 때만** 첫 회원가입을 열기 전에 5-1의 파생 인덱스 충돌 방지 절차를 적용합니다. 개발 환경에서 사용한 범위를 확인하고 담당자와 합의한 운영 시작값을 입력하세요. 이미 회원이 있는 DB에서는 이 단계를 건너뜁니다. 아래 명령은 `.env.prod`에서 DB 이름과 계정을 기본값인 `teacat`으로 둔 경우입니다.

   ```bash
   read -r -p '확인한 운영 파생 인덱스 시작값(양의 정수): ' START_INDEX
   [[ "$START_INDEX" =~ ^[1-9][0-9]*$ ]] || { echo '양의 정수를 입력하세요'; exit 1; }
   docker exec prod-postgres psql -U teacat -d teacat \
     -c "ALTER SEQUENCE wallet_derivation_index_seq RESTART WITH $START_INDEX;"
   ```

5. 서버가 스키마를 만든 다음 블록체인을 올립니다. `--wait`가 성공한 뒤 `/health` 응답도 확인하세요.

   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env.prod \
     up -d --wait --no-deps blockchain
   docker logs --tail 80 prod-blockchain
   docker exec prod-blockchain wget -qO- http://127.0.0.1:4000/health
   ```

6. 프론트 **폴더 자체는 교체하지 않고 내용만 복사**합니다. nginx는 이 폴더를 바인드 마운트로 보고 있습니다. 설정을 검사한 뒤 HTTPS에서 응답하는지 확인합니다.

   ```bash
   CID=$(docker create teacat-client:prod-manual)
   docker cp "$CID:/dist/." ~/teacat/frontend/prod/
   docker rm "$CID"
   docker exec nginx nginx -t && docker exec nginx nginx -s reload
   curl -fsSI https://teacat.site/
   ```

개발 환경도 수동으로 올리려면 **운영과 다른 `dev` 브랜치·이미지 태그·시크릿 파일**을 사용합니다. 처음 실행할 때는 다음 순서대로 진행하세요.

```bash
cd ~/teacat-src
git switch dev
git pull --ff-only
docker build -t teacat-server:dev ./server
docker build -t teacat-blockchain:dev ./blockchain
docker build -t teacat-client:dev-manual \
  --build-arg VITE_USE_MOCK=true \
  --build-arg VITE_SENTRY_ENVIRONMENT=dev ./client
cp docker/docker-compose.dev.yml ~/teacat/
cd ~/teacat
docker compose -f docker-compose.dev.yml --env-file .env.dev \
  up -d --wait postgres redis rabbitmq minio
docker compose -f docker-compose.dev.yml --env-file .env.dev \
  up -d --no-deps server
docker exec dev-server wget -qO- http://127.0.0.1:8081/actuator/health
```

마지막 응답이 `"status":"UP"`일 때만 아래를 실행합니다. 아직 준비 중이거나 실패했다면 `docker logs --tail 100 dev-server`를 확인하세요.

```bash
docker compose -f docker-compose.dev.yml --env-file .env.dev \
  up -d --wait --no-deps blockchain
docker exec dev-blockchain wget -qO- http://127.0.0.1:4000/health
CID=$(docker create teacat-client:dev-manual)
docker cp "$CID:/dist/." ~/teacat/frontend/dev/
docker rm "$CID"
docker exec nginx nginx -t && docker exec nginx nginx -s reload
curl -fsSI https://dev.teacat.site/
```

모니터링은 앱이 뜬 뒤 올립니다. 저장소의 설정과 compose 파일을 복사하고, 4-4의 웹후크 URL과 `.env.monitoring` 값을 확인하세요. **운영 DB 비밀번호까지 채우고 운영 스택을 올린 경우**에는 `--profile prod`를 붙여 운영 DB 지표도 수집합니다.

```bash
cp ~/teacat-src/docker/docker-compose.monitoring.yml ~/teacat/
cp -a ~/teacat-src/docker/monitoring/. ~/teacat/monitoring/
cd ~/teacat
docker compose --profile prod -f docker-compose.monitoring.yml \
  --env-file .env.monitoring up -d
docker compose --profile prod -f docker-compose.monitoring.yml \
  --env-file .env.monitoring ps
```

**개발 환경만 올렸다면** 위 두 `docker compose` 명령에서 `--profile prod`를 빼고 실행하세요. 운영 DB 비밀번호가 없는 상태에서 프로필을 켜면 운영 DB exporter가 접속 실패를 반복합니다.

## 7. 데이터베이스

- **스키마와 기존 데이터**: 빈 DB로 처음 설치할 때는 Flyway가 서버 기동 시 `server/src/main/resources/db/migration`을 자동 적용합니다. 기존 사용자·거래를 **옮기는 설치라면** DB 백업·복원뿐 아니라 MinIO 파일 데이터와 기존 시크릿·니모닉도 함께 이전해야 합니다. 빈 DB와 빈 MinIO를 올리는 것만으로 예전 데이터와 포토카드 파일이 복구되지는 않습니다.
- **파일 규칙**: `V<yyyyMMdd>_<HHmm>__<소문자_설명>.sql`. 버전이 겹치면 Flyway 가 기동을 멈추므로 `processResources` 와 Jenkins 사전 점검이 이를 막습니다.
- **마이그레이션은 뒤로 호환되게** 작성합니다. 블루-그린 전환 중에는 옛 코드가 새 스키마 위에서 잠시 함께 돕니다. 컬럼 삭제·이름 변경은 다음 배포에서 따로 합니다.
- **시간대**: postgres 는 `-c timezone=Asia/Seoul` 로 뜨고, 서버·블록체인 컨테이너도 `TZ=Asia/Seoul` 입니다. 셋이 어긋나면 좌석 선점 만료 같은 시간 비교가 9시간 밀립니다.
- **최초 관리자**: 관리자가 0명이면 서버가 기동할 때 `ADMIN_SEED_EMAIL` / `ADMIN_SEED_PASSWORD` 로 하나 만듭니다 (멱등).
- **접속**: 운영 DB의 5432번 포트는 호스트에도 공개하지 않습니다. SQL을 직접 확인하려면 EC2에 SSH로 접속해 컨테이너 안의 `psql`을 실행합니다. 아래 명령의 `SERVER_PUBLIC_IP`를 실제 IP나 SSH 호스트명으로 바꾸세요.

```bash
ssh -t ubuntu@SERVER_PUBLIC_IP 'docker exec -it prod-postgres psql -U teacat -d teacat'
```

이 명령은 **관리자 PC에서** 실행합니다. 이미 EC2 셸에 있다면 `docker exec -it prod-postgres psql -U teacat -d teacat`만 실행하세요. 기존 문서의 `ssh -L 5432:localhost:5432` 방식은 DB 포트가 호스트에 열려 있지 않아 연결되지 않습니다.

## 10. 로컬 개발 환경

필요한 프로그램은 **JDK 21, Node.js 22와 npm, Docker Desktop(또는 Docker Engine + Compose v2)**입니다. 명령은 저장소 루트에서 시작하고, 서버·블록체인·프론트는 **서로 다른 터미널**에서 실행하세요. 아래 코드는 Bash 기준이며, Windows PowerShell에서 다른 명령이 필요한 부분은 바로 아래에 따로 적었습니다.

1. **DB·Redis·RabbitMQ·MinIO 준비.** Docker Desktop이 실행 중인지 확인한 다음 저장소 루트에서 올립니다. 로컬 계정은 `docker/docker-compose.yml`에 개발 전용 값으로 들어 있습니다.

   ```bash
   docker compose -f docker/docker-compose.yml up -d
   docker compose -f docker/docker-compose.yml ps
   ```

2. **블록체인 서비스 준비.** `npm install`의 설치 후 스크립트가 `blockchain/.env`가 없을 때 자동으로 만듭니다. 이미 파일이 있으면 유지하므로 `setup:env`를 다시 실행할 필요는 없습니다. 새 터미널에서 다음을 실행합니다.

   ```bash
   cd blockchain
   npm install
   npm run dev
   ```

   `http://localhost:4000/health`에서 상태를 확인하세요. 자동 생성된 개인키로는 팀이 배포한 컨트랙트의 관리자 기능을 실행하지 못할 수 있습니다. 해당 기능이 필요하면 팀에서 **역할이 확인된 키**를 전달받아 `blockchain/.env`의 `OPERATOR_PRIVATE_KEY`를 바꾸세요. 개발용으로 자동 생성된 니모닉·키를 운영에 사용하지 마세요.

3. **API 서버 준비.** 다른 터미널에서 `server/.env.example`을 `server/.env`로 복사합니다. 파일의 `BLOCKCHAIN_INTERNAL_API_KEY`에는 `blockchain/.env`의 `INTERNAL_API_KEY`와 **같은 값**을 넣으세요. 값을 채팅이나 커밋에 남기지 마세요.

   ```bash
   cd server
   cp -n .env.example .env
   ./gradlew bootRun
   ```

   Windows PowerShell에서는 `cp -n` 대신 아래 명령을 사용합니다.

   ```powershell
   cd server
   if (-not (Test-Path .env)) { Copy-Item .env.example .env }
   .\gradlew.bat bootRun
   ```

   기동 후 API 주소는 `http://localhost:8080/api`, Swagger는 `http://localhost:8080/api/swagger-ui/index.html`입니다. 결제·Pinata 키를 비워 두면 그 기능은 동작하지 않지만 다른 개발 경로는 실행할 수 있습니다.

4. **프론트엔드 실행.** 또 다른 터미널에서 실행합니다. `http://localhost:5173`에 접속하면 Vite가 `/api` 요청을 로컬 서버의 8080번 포트로 넘깁니다.

   ```bash
   cd client
   npm install
   npm run dev
   ```

문제가 생기면 `docker compose -f docker/docker-compose.yml ps`에서 인프라 상태를 먼저 보고, 블록체인의 `/health`, 서버 기동 로그, 브라우저 개발자 도구의 `/api` 응답을 차례로 확인하세요. 테스트는 각각 `server/`에서 `./gradlew test`(Windows: `.\gradlew.bat test`), `blockchain/`에서 `npm test`를 실행합니다.

## 11. 설치 후 확인과 문제 해결

배포가 끝나면 다음을 확인합니다. 개발 환경은 명령의 `prod`를 `dev`로 바꾸고, 서버 컨테이너 이름은 `dev-server`를 사용하세요. 운영 blue·green의 현재 색은 `prod-backend.inc`에 기록되어 있습니다.

```bash
cd ~/teacat
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
cat nginx/conf.d/prod-backend.inc
curl -fsSI https://teacat.site/
docker exec prod-blockchain wget -qO- http://127.0.0.1:4000/health
```

브라우저에서는 첫 화면, 로그인, 이미지 한 장, 관리자 기능을 차례로 확인하세요. 결제·Pinata·SSAFY 로그인처럼 외부 키가 필요한 기능은 해당 키와 외부 서비스 설정을 마친 뒤 확인합니다. 모니터링을 켰다면 `/dashboard/`에서 대상 서버 지표가 들어오는지도 확인하세요.

| 증상 | 먼저 확인할 곳 |
|---|---|
| 인증서 발급 실패 | 두 도메인의 DNS와 외부 80번 포트, `docker logs --tail 100 nginx`, 4-3의 임시 HTTP 설정 |
| compose에서 필수 변수 오류 | `~/teacat/.env.dev` 또는 `.env.prod`의 빈 값과 5장의 예시 파일. 값을 출력하는 `docker compose config` 결과는 공유하지 않기 |
| 사이트는 열리지만 `/api/`가 502 | `prod-backend.inc`의 현재 색, 해당 서버의 `docker logs`, 서버 `8081/actuator/health` 상태 |
| 블록체인 컨테이너가 시작되지 않음 | 서버가 먼저 `UP`인지, `docker logs --tail 100 prod-blockchain`, 역할 키·DB 접속 값 |
| 이미지 업로드·조회 실패 | MinIO 컨테이너 상태, `MINIO_PUBLIC_BASE_URL`, nginx `/storage/` 설정. 업로드 403이면 서명에 사용한 Host가 맞는지 확인 |
| 프론트가 403/404 또는 빈 화면 | `~/teacat/frontend/<환경>/index.html` 존재와 nginx 설정 검사(`docker exec nginx nginx -t`) |

운영할 때 다음 원칙도 지킵니다.

- **dev·prod 스택이 같은 `teacat-net`에 있으므로** 컨테이너끼리는 서비스 이름(`postgres`) 대신 **컨테이너 이름(`prod-postgres`)**으로 부릅니다. 서비스 이름을 쓰면 도커 DNS가 두 스택 사이를 라운드로빈할 수 있습니다.
- 서버에서 직접 고친 nginx 환경별 conf·앱 compose 파일은 다음 Jenkins 배포 때 저장소 내용으로 **덮어써집니다.** 단, `prod-backend.inc`, `nginx.conf`, `docker-compose.proxy.yml`은 자동으로 덮지 않습니다.
- 바인드 마운트된 파일·폴더는 `mv`로 교체하지 말고 `cp`로 내용만 덮어씁니다. 교체하면 컨테이너가 옛 파일을 계속 볼 수 있습니다.
- `monitoring/alertmanager/webhook_url`이 없는 채로 모니터링을 올리면 Docker가 그 경로에 디렉터리를 만들어 Alertmanager가 실패합니다. 먼저 **파일**을 만들고 실제 URL을 채우세요.
- 운영 서버 컨테이너는 `mem_limit: 2g`입니다. 운영 Swagger는 앱과 nginx 양쪽에서 꺼져 있습니다. API 문서는 [개발 Swagger](https://dev.teacat.site/api/swagger-ui/index.html)에서 확인합니다.
